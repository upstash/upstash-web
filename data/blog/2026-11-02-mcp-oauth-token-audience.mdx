This guide follows the [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), revision **2026-07-28**, the current one as of November 2026. The rules below have been part of the spec since revision 2025-06-18.

The spec asks for two things that are easy to skip:

- The **client** tells the authorization server which MCP server the token is for.
- The **MCP server** only accepts tokens that were made for it.

Without the second check, a token made for one service can be used on another. Here is how we added it to the Context7 MCP server, and what to watch for if you do the same.

## Who does what?

| Who | What it does |
| --- | --- |
| MCP client | Sends a `resource` parameter, the MCP server's URL, when it asks for a token. |
| Authorization server | Writes that URL into the token's audience (`aud`). |
| MCP server | Rejects any token whose audience is not its own URL. |

One more rule: an MCP server must never pass the token it received on to another API.

## Step 1: Check tokens locally

If your tokens are opaque, your server has to ask the authorization server about every one of them. Use signed JWT access tokens instead and check them yourself:

```ts
import { createRemoteJWKSet, jwtVerify } from "jose";

const jwks = createRemoteJWKSet(new URL(`${ISSUER}/.well-known/jwks.json`));

const { payload } = await jwtVerify(token, jwks, {
  issuer: ISSUER,
  audience: "https://mcp.example.com",
});
```

The `audience` option does the audience check for you: a token made for another server fails.

**If the authorization server is down and you can't check a token, answer 503 ("try again later"), not 401 ("your token is bad").** Clients read a 401 as "sign in again". If many of them do that at once, a short outage turns into a wave of sign-ins.

## Step 2: Get the audience into tokens

Turn on the authorization server's setting that copies `resource` into `aud`. It only applies to new sign-ins, so tokens from older sign-ins won't have an audience yet.

Some authorization servers add the audience to an older sign-in when the client refreshes its token with a `resource`. Once set, it can't change: a refresh with a different `resource` fails.

## Step 3: Turn the check on slowly

Don't reject on day one. First log every token whose audience doesn't match, and keep accepting it. The log shows you what real clients send:

- **Some clients send the URL exactly as the user configured it**, with a path or a query string. Decide which forms of your URL you accept before you start rejecting.
- **Some users reach you through a gateway** that signs them in itself. Its tokens carry the gateway's address, not yours. When you reject them, say what to do instead, for example "use an API key". Otherwise the client just keeps signing in again.

Then reject tokens made for other servers. Last, once old sign-ins have refreshed, reject tokens with no audience at all.

## What if a client doesn't send `resource`?

Some clients leave `resource` out when they start the sign-in. Once audiences are enforced, their sign-in fails.

You can fix this on your side. If a sign-in request has no `resource`, send it back to the authorization server with your MCP server's URL added. Mark the request, so that a request that still has none gets an error instead of going round in circles.

## Why do users get logged out after a refresh?

Most authorization servers give out a new refresh token on every refresh, and treat reuse of an old one as theft: they cancel the whole sign-in. So a client that refreshes twice at the same moment logs its own user out.

The fix is in the client: refresh one at a time, and save the new refresh token before anything else uses it.

## Should clients register dynamically or use a metadata URL?

Newer revisions of the spec prefer **Client ID Metadata Documents**: instead of registering, a client identifies itself with a URL that describes it. If your authorization server supports them, let it handle them, and list it first in your server's metadata. Don't build this into a proxy of your own in front of it. That leads to the "confused deputy" problem the spec warns about.

## Checklist

**For your MCP server:**

- Publish Protected Resource Metadata, so clients know where to sign in.
- Check JWT access tokens yourself, including the audience.
- If you can't check a token because the authorization server is down, answer 503 ("try again later"), not 401.
- Log mismatches first, then reject other servers' tokens, then tokens with no audience.
- Explain every rejection in plain words.
- Never forward a client's token to another API.

**For your MCP client:**

- Send the same `resource` when you sign in, get a token and refresh it.
- Refresh one at a time, and save the new refresh token first.
- Read 401 as "sign in again" and 503 as "try again later".
