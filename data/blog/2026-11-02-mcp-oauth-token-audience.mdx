This guide follows the [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), revision **2026-07-28**, the current one as of November 2026. The rules below have been part of the spec since revision 2025-06-18.

The spec asks for two things that are easy to skip:

- The **client** tells the authorization server which MCP server the token is for.
- The **MCP server** only accepts tokens that were made for it.

Without the second check, a token made for one service can be used on another. We added it to the Context7 MCP server recently. This post covers the steps and the problems we ran into along the way, so you can avoid them.

## Who does what?

| Who | What it does |
| --- | --- |
| MCP client | Sends a `resource` parameter, the MCP server's URL, when it asks for a token. |
| Authorization server | Writes that URL into the token's audience (`aud`). |
| MCP server | Rejects any token whose audience is not its own URL. |

One more rule: an MCP server must never pass the token it received on to another API.

## The steps

**1. Check tokens locally.** If your tokens are opaque, your server has to ask the authorization server about every one of them. Use signed JWT access tokens instead and check them yourself:

```ts
import { createRemoteJWKSet, jwtVerify } from "jose";

const jwks = createRemoteJWKSet(new URL(`${ISSUER}/.well-known/jwks.json`));

const { payload } = await jwtVerify(token, jwks, {
  issuer: ISSUER,
  audience: "https://mcp.example.com",
});
```

The `audience` option does the audience check for you: a token made for another server fails.

**2. Get the audience into tokens.** Turn on the authorization server's setting that copies `resource` into `aud`.

**3. Turn the check on slowly.** First log every token whose audience doesn't match, and keep accepting it. Then reject tokens made for other servers. Last, reject tokens with no audience at all.

That's the whole plan. The rest of this post is about what can go wrong.

## Problems you may run into

### Users get logged out when your authorization server has a bad minute

**Why:** if your server can't check a token because the authorization server is slow or down, it's tempting to answer 401. But clients read 401 as "your sign-in is gone" and start a new sign-in or refresh. When many clients do that at once, a short outage turns into a wave of sign-ins that keeps the authorization server overloaded.

**Fix:** check tokens locally (step 1), so most requests don't need the authorization server at all. When you still can't decide, answer 503 ("try again later"), not 401. Keep 401 for tokens that are certainly bad.

### Sign-in fails after you turn on audiences

**Why:** some clients leave `resource` out when they start the sign-in, but send it later when they ask for the token. The authorization server sees a token request for a resource that was never approved, and refuses it.

**Fix:** if a sign-in request has no `resource`, send it back to the authorization server with your MCP server's URL added. Mark the request, so that one that still has none gets an error instead of going round in circles. The audience comes from the sign-in, so the token request then works whether or not it repeats `resource`.

### Old sign-ins never get an audience

**Why:** the audience setting only applies to new sign-ins. Older ones keep issuing tokens without `aud`, sometimes for months, because refresh tokens often don't expire.

**Fix:** some authorization servers add the audience to an older sign-in when the client refreshes with a `resource`. If yours does, old sign-ins fix themselves as clients refresh. Clients that refresh without `resource` stay without an audience. So keep accepting tokens with no audience until they are a small share, and measure that share before you require one.

Be careful with that refresh trick: once a sign-in has an audience, it usually can't change, and a later refresh with a different `resource` fails. Only add a `resource` on a client's behalf when you know which one its sign-in should have.

### The same server has several URLs

**Why:** clients send the URL the user typed. You may see `https://mcp.example.com`, `https://mcp.example.com/mcp`, a trailing slash, or a query string such as `?client=…`, all meaning the same server.

**Fix:** decide which forms you accept before you start rejecting, and compare them in a normalized way. The log from step 3 tells you which ones real clients send.

### Users behind a gateway keep signing in again

**Why:** some users reach you through an API gateway that runs its own sign-in. Its tokens carry the gateway's address, so a correct audience check rejects them. If the error only says "invalid token", the client signs in again, gets the same kind of token, and loops.

**Fix:** reject these tokens with a message that says what to do instead, for example "use an API key with this gateway".

### Rejecting in two places causes a loop

**Why:** if both your MCP server and an API behind it check the audience, and only the API starts rejecting, the MCP server may read the API's answer as an expired token and ask the client to sign in again, over and over.

**Fix:** turn the stricter mode on at the edge first (the server the client talks to), and only then behind it.

### Users get logged out after a refresh

**Why:** most authorization servers give out a new refresh token on every refresh and treat reuse of an old one as theft: they cancel the whole sign-in. A client that refreshes twice at the same moment, from two tabs or two processes, logs its own user out.

**Fix:** there's nothing the server can do here. In your client, refresh one at a time, and save the new refresh token before anything else uses it.

### You can't tell which clients will break

**Why:** without data, you can't tell whether turning on a check will break a popular client.

**Fix:** log each mismatch with the client ID and the kind of mismatch (no audience, or someone else's). Skip the log on very busy endpoints such as health or token checks, or it will bury everything else.

## Should clients register dynamically or use a metadata URL?

Newer revisions of the spec prefer **Client ID Metadata Documents**: instead of registering, a client identifies itself with a URL that describes it. If your authorization server supports them, let it handle them, and list it first in your server's metadata. Don't build this into a proxy of your own in front of it. That leads to the "confused deputy" problem the spec warns about.

## Checklist

**For your MCP server:**

- Publish Protected Resource Metadata, so clients know where to sign in.
- Check JWT access tokens yourself, including the audience.
- If the authorization server is down and you can't check a token, answer 503 ("try again later"), not 401.
- Log mismatches first, then reject other servers' tokens, then tokens with no audience.
- Add a default `resource` to sign-ins that leave it out.
- Explain every rejection in plain words.
- Never forward a client's token to another API.

**For your MCP client:**

- Send the same `resource` when you sign in, get a token and refresh it.
- Refresh one at a time, and save the new refresh token first.
- Read 401 as "sign in again" and 503 as "try again later".
