AI agents can read pages, click buttons and fill out forms. But they still have to guess what a website can do from an interface built for people.

[WebMCP](https://github.com/webmachinelearning/webmcp) gives them a direct path. A website can register structured tools that browser agents discover and call from the page.

For a library website, that tool could search the docs. Instead of making an agent scan page after page, we can expose a `query_library_docs` tool and use [Context7](https://context7.com) to retrieve the right documentation in the background.

Let's build it.

## How It Works

Here is what happens when an agent calls the tool:

1. A browser agent opens your library website.
2. The page registers a WebMCP documentation tool.
3. The agent calls the tool with a question.
4. Your server sends the question to Context7.
5. Context7 returns relevant documentation and code examples.

Your website controls the tool and how it behaves. Context7 handles ingesting, updating and retrieving the documentation.

WebMCP does not replace a regular MCP server. You configure a regular MCP server in an IDE or agent client. A WebMCP tool belongs to the open page and can use the current browser session. It is a good fit when a person and an agent are working on the same website.

## Before You Start

You need:

- A library indexed by Context7
- A Context7 API key
- A server endpoint in your website
- Chrome 149 or later with experimental WebMCP support enabled

You can find the library ID in the URL of its Context7 page. The ID for Next.js, for example, is `/vercel/next.js`.

Keep this ID on the server. The tool only needs to answer questions about your library, so the agent should not be able to choose a different ID.

## Create a Context7 Endpoint

First, add a server endpoint that takes a question and sends it to the [Context7 API](https://context7.com/docs/api-guide).

The following example uses a Next.js route handler:

```ts title="app/api/agent/docs/route.ts"
const CONTEXT7_LIBRARY_ID = "/acme/acme-sdk";

export async function POST(request: Request) {
  const body = (await request.json()) as { query?: unknown };

  if (
    typeof body.query !== "string" ||
    body.query.length < 1 ||
    body.query.length > 500
  ) {
    return Response.json(
      { error: "Query must contain between 1 and 500 characters." },
      { status: 400 },
    );
  }

  const url = new URL("https://context7.com/api/v2/context");
  url.searchParams.set("libraryId", CONTEXT7_LIBRARY_ID);
  url.searchParams.set("query", body.query);
  url.searchParams.set("type", "txt");

  const response = await fetch(url, {
    headers: {
      Authorization: `Bearer ${process.env.CONTEXT7_API_KEY}`,
    },
  });

  if (!response.ok) {
    return Response.json(
      { error: "Context7 documentation lookup failed." },
      { status: response.status },
    );
  }

  return Response.json({
    libraryId: CONTEXT7_LIBRARY_ID,
    context: await response.text(),
  });
}
```

Add your Context7 API key to the server environment:

```bash title=".env.local"
CONTEXT7_API_KEY=ctx7sk_your_key
```

Keep the API key out of client-side code. WebMCP tools run in the page, where users, browser extensions and other scripts could read it.

## Register the WebMCP Tool

Now register a tool when the page loads:

```js
const modelContext = document.modelContext;

if (modelContext) {
  const registration = new AbortController();

  await modelContext.registerTool(
    {
      name: "query_library_docs",
      title: "Search library documentation",
      description:
        "Retrieves current documentation and code examples for the Acme SDK.",
      inputSchema: {
        type: "object",
        properties: {
          query: {
            type: "string",
            description:
              "A specific implementation or API question about the Acme SDK.",
            minLength: 1,
            maxLength: 500,
          },
        },
        required: ["query"],
        additionalProperties: false,
      },
      annotations: {
        readOnlyHint: true,
        untrustedContentHint: true,
      },
      async execute({ query }, { signal } = {}) {
        const response = await fetch("/api/agent/docs", {
          method: "POST",
          headers: {
            "Content-Type": "application/json",
          },
          body: JSON.stringify({ query }),
          signal,
        });

        if (!response.ok) {
          const result = await response.json().catch(() => null);
          throw new Error(result?.error ?? "Documentation lookup failed.");
        }

        return response.json();
      },
    },
    { signal: registration.signal },
  );

  // Call registration.abort() when this page or component is removed.
}
```

The feature check keeps the site working in browsers without WebMCP. Everyone still gets the normal documentation site. Supported agents also get the structured tool.

The annotations tell compatible agents that this tool only reads data and that its result comes from an external source. The registration `AbortSignal` removes the tool when the page or component is no longer active.

Chrome versions differ in whether they pass the second argument to `execute`, so the example defaults it to an empty object. Browsers that provide the execution signal can still cancel the Context7 request.

## Make the Tool Page-Aware

WebMCP gets more useful when the tool knows which page is open.

For example, a versioned documentation site can register the library ID for the selected version:

```ts
const LIBRARY_IDS = {
  latest: "/acme/acme-sdk",
  v2: "/acme/acme-sdk/v2.8.0",
  v1: "/acme/acme-sdk/v1.14.2",
} as const;
```

Keep this mapping on the server and accept only known versions. You can also include the current page in the query:

```js
body: JSON.stringify({
  query: `Current page: ${location.pathname}\nQuestion: ${query}`,
}),
```

Now the agent does not have to explain what it is looking at. The page already provides that context.

## Test the Integration

WebMCP is still experimental. For local development, open this flag in Chrome 149 or later:

```text
chrome://flags/#enable-webmcp-testing
```

Set it to **Enabled**, relaunch Chrome, start your local server and open its full URL, including the port. For example:

```text
http://localhost:3000
```

Run this in DevTools on that page:

```js
document.modelContext;
```

It should return an object. If it returns `undefined`, make sure you are on your application page rather than a Chrome error page and that Chrome was relaunched after enabling the flag.

You can discover and invoke the tool directly from DevTools:

```js
const tools = await document.modelContext.getTools();
const tool = tools.find(({ name }) => name === "query_library_docs");

await document.modelContext.executeTool(
  tool,
  JSON.stringify({ query: "How do I authenticate?" }),
);
```

`executeTool` expects the input arguments as a JSON string. You can also inspect registered tools with the [Model Context Tool Inspector](https://developer.chrome.com/docs/ai/webmcp/#imitate-agent-chat-with-the-inspector-extension).

WebMCP also requires an origin-isolated document. Do not disable origin isolation with `document.domain` or an `Origin-Agent-Cluster: ?0` header.

The Chrome flag is only for local development. To make WebMCP available to visitors during the experiment, register your deployed origin for the [WebMCP origin trial](https://developer.chrome.com/origintrials/#/view_trial/4163014905550602241) and add its token to your pages as an `Origin-Trial` response header or meta tag.

Try questions such as:

- How do I authenticate with the Acme SDK?
- Show me the current pagination API.
- How can I migrate this example from version 1 to version 2?

Make sure the agent selects `query_library_docs`, the server uses the expected library ID, and cancellation and error responses work.

Before deploying, add the usual server protections:

- Authentication where needed
- Rate limiting
- Input validation
- Request logging
- Response caching
- Context7 error and quota handling

## Conclusion

WebMCP gives browser agents a structured way to use the current website. Context7 gives those tools current, version-specific library documentation.

Together, they make a documentation site agent-ready with a small amount of code. People keep the same website, agents get a reliable docs tool, and the library team does not have to build its own crawling and retrieval system.

WebMCP is still experimental, so ship this as a progressive enhancement and follow the [WebMCP repository](https://github.com/webmachinelearning/webmcp) for API changes.
