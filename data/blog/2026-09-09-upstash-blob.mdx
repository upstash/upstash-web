Today we are launching Upstash Blob, object storage for the files your application stores and serves.

Most applications running on Upstash keep their state in three places: keys in Redis, messages in QStash, and files somewhere else. The files were the part we did not offer, so every one of those apps had a bucket from another provider and a few hundred lines of glue between the two. Blob is the bucket, and the SDK is the glue, written once.

<Summary>
  - **Global storage, no region to choose.** Use our SDK or the AWS SDK through an S3-compatible API.
  - **Public or private, your choice.** Public files are served through a global CDN.
  - **Files from a browser go straight to the bucket.** Your server authorizes the upload and never touches the bytes.
  - **Free to start.** Get 1 GB of storage and 10 GB of bandwidth per month. No credit card required.
</Summary>

## What we wanted from a bucket

We had a short list. It should be a real bucket, with objects under paths and an S3 API, so nothing you build on it depends on our SDK. It should not ask where to put your data, because the answer for files served to users is always "close to them". And it should know the difference between a product image and an invoice without you writing an access layer.

So a bucket is created with a name, a visibility, and nothing else. Public buckets give every object a URL on the bucket's own hostname, cached at the edge. Private buckets have no public URL at all; every read is a signed link that expires. Both hand you one token, and that token is the whole configuration:

```ts
import { Bucket } from "@upstash/blob"

const bucket = Bucket.fromEnv()

const blob = await bucket.put("reports/q3.pdf", pdf, {
  contentType: "application/pdf",
})
blob.url // https://b3f9a2c7d1e4.blob.upstash.io/reports/q3.pdf

const { url } = await bucket.signedReadUrl("invoices/2026-0042.pdf", {
  expiresIn: "5m",
})
```

The SDK learns whether it is talking to a public or a private bucket from the backend, so the same code runs against both. On a private bucket `url` is simply `undefined`, and objects are stored with `Cache-Control: private` so no shared cache keeps a copy.

The token itself never signs a request. It is exchanged for short-lived credentials scoped to that one bucket, and those are what sign every `put`, `get` and `list`. The SDK does the exchange on first use and refreshes before expiry, so you never see it happen. It is also why S3 compatibility is not a separate mode: `bucket.s3()` hands the same credentials to the AWS SDK or the AWS CLI, for anything we do not wrap. Byte ranges, conditional GETs, delimiters, object tagging, and every tool that already speaks S3.

Upstash buckets are global without a region selector: a reader in Singapore and a reader in Frankfurt are both served from close by, and there is one rate sheet instead of one per region.

## File uploads without the boilerplate

The SDK is the biggest reason to choose Upstash Blob. We designed it so adding file uploads means writing the parts that belong to your app: who can upload, what you accept, and what happens when a file arrives. Sensible defaults handle the transport, and **end-to-end type safety** connects your server logic all the way to the component that renders the result.

Start with a handler. This one accepts images and PDFs from signed-in users, gives each file a unique path, and saves a database record when it lands. `getUser` and `db` are your app's existing auth and database helpers:

```ts
// lib/uploads.ts
import "server-only"
import { BlobError, uniquePath, uploadHandler } from "@upstash/blob"
import { getUser } from "./auth"
import { db } from "./db"

export const uploads = uploadHandler({
  constraints: { maxSize: "20mb", contentTypes: ["image/*", "application/pdf"] },

  onBeforeUpload: async ({ request, file }) => {
    const user = await getUser(request)
    if (!user) throw new BlobError("unauthorized")
    return { path: uniquePath`${user.id}/${file.name}`, metadata: { owner: user.id } }
  },

  onUploadComplete: async ({ uploadId, path, url, metadata }) => {
    await db.files.upsert({ uploadId, owner: metadata.owner, path, url })
    // Sent to the client as upload.blob.data, with its type inferred end to end.
    return { fileId: uploadId }
  },
})
```

The handler reads `UPSTASH_BLOB_TOKEN` automatically. In Next.js, mounting it takes two lines:

```ts
// app/api/upload/route.ts
import { uploads } from "@/lib/uploads"
export const { GET, POST } = uploads
```

Then connect your UI to the handler's type:

```tsx
"use client"
import { uploadHooks } from "@upstash/blob/react"
import type { uploads } from "@/lib/uploads"

const { useUpload } = uploadHooks<typeof uploads>()

export function FilePicker() {
  const { start, upload, accept } = useUpload()

  return (
    <>
      <input
        type="file"
        accept={accept}
        onChange={(e) => start({ file: e.target.files?.[0] })}
      />
      {upload?.pending && <progress value={upload.percent} max={100} />}
      {upload?.status === "error" && <p>{upload.error.message}</p>}
      {upload?.status === "done" && <p>Saved file {upload.blob.data.fileId}</p>}
    </>
  )
}
```

That `fileId` is inferred from `onUploadComplete`. Rename it on the server and TypeScript points to the component that needs updating.

Add named routes and `useUpload("avatar")` only accepts names your handler defines. For uploads that need extra data, an [input schema](https://upstash.com/docs/blob/uploads/upload-handler#uploadroute) gives you both server validation and a typed `start({ file, input })` call.

No duplicate request and response interfaces, code generation, or type assertions to keep the two sides in sync. The client imports only a type, so your server code stays on the server.

The defaults do just as much work. The hook already knows to call `/api/upload`. Its `accept` value comes from your handler's allowed file types, and the server enforces your size and type constraints. Files over 16 MB automatically use multipart uploads, with pause, resume, retries for failed parts, and refreshed upload signatures when they expire. Small and large files expose the same progress and error state to your UI. You can change the defaults when your app needs it; the [upload client](https://upstash.com/docs/blob/uploads/upload-client) and [large-file docs](https://upstash.com/docs/blob/uploads/large-files) cover the controls.

Underneath that small API, files travel directly from the browser to storage. Your handler authorizes the upload and verifies the result, while file bytes bypass your application server and its request body limit:

## Small decisions that add up

A few things in the SDK are the way they are on purpose, and are worth explaining.

`put` overwrites by default. A write you retry after a timeout should not fail because the first attempt actually landed. When overwriting is the wrong thing, you say so: `allowOverwrite: false` refuses if anything is at the path, and `ifUnchanged` with an etag refuses if the object changed since you read it. Both are enforced by storage, so there is no window between the check and the write. `updateJson` builds a read-modify-write loop on top of that and retries on conflict, which turns a JSON object in a bucket into something you can safely update from two places at once.

Paths reject `.` and `..` segments rather than normalizing them. A filename that came from a browser goes through `uniquePath`, which reduces it to a slug with a random suffix, so `../admin/x.png` becomes `x-9fQ2mAe7.png` and can never climb into another directory.

`Cache-Control` is chosen at upload, per object, and every object also carries a `versionedUrl` with its etag on the query. Store an avatar at a stable path with `cache: "immutable"`, save the versioned URL on the user's row, and you have an image that is cached for a year and still changes the moment the user picks a new one. Nothing to invalidate, nothing to delete.

A signed link comes back with `expiresAt`, not just the duration you asked for, because a link cannot outlive the credential that signed it. Cache the link until then, and you never hand out a URL that has already died.

And one thing we deliberately did not build: a query layer. `list` filters by prefix and nothing else. There is no search by owner, type or date, because your application already has a database that does that well, and the row it writes in `onUploadComplete` is the index. The bucket holds the bytes. We think that division is the right one, and the SDK is shaped around it.

## Pricing

We wanted one rate sheet, and no region means we can have one. Pay as you go is **$0.02 per GB** stored per month, **$0.02 per GB** served, $0.30 per million reads and $4.50 per million writes, lists and copies. Bandwidth means egress only: data transferred out of your bucket. Uploads cost nothing to transfer, deletes are free, and storage is billed on the monthly average of the bucket rather than its peak. A read served from the CDN costs the same as one served from origin, and nothing rounds up to a whole unit.

The free tier is 1 GB of storage, 10 GB of bandwidth, 10,000 reads and 2,000 writes a month, with no card. The full breakdown is on the [pricing page](https://upstash.com/pricing/blob).
